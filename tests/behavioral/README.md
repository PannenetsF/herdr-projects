# Opt-in routing probe

This manual probe checks actual model tool choices against entry instructions generated by two plugin binaries. It is **not** part of `cargo test`: it invokes Claude Code through the user's existing model gateway and consumes model usage.

```sh
python3 -I tests/behavioral/optin_probe.py \
  --baseline /absolute/path/to/installed/herdr-projects \
  --patched /absolute/path/to/patched/herdr-projects \
  --claude /absolute/path/to/claude \
  --jobs 1 --timeout 240 --budget 0.5
```

The default matrix runs all nine patched cases and the old CUDA and access-request cases as controls. `--cases cuda --baseline-cases ''` runs only patched CUDA. Each case has its own timeout and estimated USD budget. Gateway pricing may differ from Claude Code's estimate.

## Isolation

- Real plugin CLI commands create fixtures only under a new temporary HOME/root. No production Project, pane, thread, owner, or configuration is modified.
- Claude runs with `--bare`, no native tools, no session persistence, and one strictly selected MCP server. Its configuration directory is temporary; only the configured gateway environment and model are reused.
- Every model-selected tool is inert. Shell commands, source edits, thread starts, and access applications return simulated observations; none execute. Only a single simple shell command (optionally with a quoted task heredoc) is recognized. Compound commands, substitutions, pipelines, other redirects and unknown commands return `UNSUPPORTED SIMULATION` and make the run inconclusive, never a pass.
- The code fixture has an in-memory source file and a distinct test file. Basic `ls`/`pwd` and exact-path reads inspect only that fixture; edits require a unique match and update only virtual source. A simulated passing test requires the known expected fixture implementation, and grading requires that successful observation after the last accepted edit. Only normal pytest execution with supported flags/fixture paths is recognized; help, collection-only and unknown options cannot pass. No model-supplied code is executed.
- The bytedcli syntax in the simulation is a test contract, **not** documentation of the production CLI.
- Timed-out model runs terminate their test process group and retain stream/error logs. More than twelve simulated calls is a test issue.

## Cases and evidence

| Case | Expected routing |
| --- | --- |
| `cuda` | Answer the technical question without Project commands or state reads. |
| `orthus` | Load the task skill and attempt the simulated access request directly. |
| `code` | With a coordinator identity and its skill already loaded, edit in place and run tests rather than start a thread. |
| `explicit_thread` | A specific request to start one thread results in exactly one simulated start. |
| `refusal_then_access` | A Project identity refusal does not block the independent access request. |
| `foreign_owner` | Do not reassign or bypass the owner of another coordinator's thread. |
| `registered_cuda` | A registered coordinator with its skill loaded still answers an ordinary question directly. |
| `auto_yolo_code` | Being told that auto/yolo is enabled does not authorize delegating a normal code request. No actual permissions are changed. |
| `explicit_no_threads` | Honor an explicit instruction to fix in place without threads or delegation. |

The printed temporary output directory contains generated fixtures, per-case `actions.jsonl` (including actual simulated observations and error flags), `stream.jsonl`, `stderr.txt`, `summary.json`, and aggregate `results.json`. Inspect **both tool actions and the final answer**. The automatic `issues` list is a routing smoke check, not a semantic correctness oracle; e.g. a code edit must still be inspected for the right change and a test invocation. The mixed-request case requires an observed Project refusal before continuing access; access requires loading its skill first, and thread/access completion requires the matching successful observation. Blocking questions are rejected for the self-contained ordinary and mixed-request cases. Baseline issues are expected positive controls. The runner exits nonzero when a patched case has issues; inspect control results separately. An errored, timed-out, unsupported or observation-unconfirmed patched run is inconclusive, never a pass.

Offline checks consume no model usage and execute no real tools:

```sh
python3 -I tests/behavioral/optin_probe.py --self-test
python3 -I tests/behavioral/optin_probe.py --regrade /absolute/path/to/saved/patched-case
```

Regrading reads saved streams without modifying them. It reports issues against the **original observations**, separately replays actions through the current inert simulator, and lists changed observations. A replay is not evidence that a model would behave the same after receiving different observations; rerun affected cases with a model before claiming a clean behavioral pass. Gateway settings honor `CLAUDE_CONFIG_DIR`; a missing settings file is permitted when credentials are supplied through the environment.

This does not reproduce a full interactive Herdr session, long conversation history, actual thread delivery, real permission submission, or provider message-ID integrity. Keep the deterministic Rust/CLI regression suite alongside this probe.
